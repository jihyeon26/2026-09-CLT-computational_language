# 연습 1 노트북 흐름 정리

대상 노트북: `CLT_Morning_1_From_AI_News_to_a_Tiny_Knowledge_Graph.ipynb`

## 1. 이 노트북에서 하는 일

합성 AI 뉴스 문서에서 출발해, 문장과 개체를 추출하고 근거가 있는 관계만 선별한 뒤 작은 지식 그래프를 만든다. 마지막에는 그래프를 질의하고 추출 성능까지 평가한다.

핵심은 **트리플을 많이 만드는 것**이 아니라 다음 두 조건을 만족하는 것이다.

1. 각 관계가 어떤 원문 근거에서 나왔는지 추적할 수 있어야 한다.
2. 추출 과정에서 생긴 오류를 단계별로 확인하고 평가할 수 있어야 한다.

전체 흐름은 다음과 같다.

```text
원문·메타데이터 보존
  → 문서 점검과 중복 탐색
  → 문장 분할과 원문 위치(offset) 저장
  → 질문에 맞는 개체·관계 스키마 설계
  → 개체 언급 탐지
  → 표기 정규화와 표준 개체 연결
  → 근거가 있는 관계·이벤트 추출
  → 형식·타입·근거 검증
  → 지식 그래프 생성
  → 그래프 질의
  → 정답셋 기반 평가와 오류 개선
```

## 2. 단계별 실행 흐름

| 단계 | 노트북 구간 | 입력 | 핵심 처리 | 주요 출력 |
|---|---|---|---|---|

| 11 | `11 · Structured LLM extraction` | 스키마, 문서, 모의 LLM JSON | Pydantic으로 구조를 검사하고 인용 근거가 원문에 있는지 확인 | 검증된 후보 또는 거절 사유 |

## 3. 데이터가 어떻게 바뀌는가

### 3.1 문서: `docs`

원문과 메타데이터를 보존하는 기준 테이블이다. 이후 단계에서 원문을 덮어쓰지 않고, 문장·언급·관계 같은 파생 테이블을 별도로 만든다.

```text
doc_id + title + publisher + published_at + track + source_url + text
```

여기서 먼저 확인하는 항목은 결측치, 문서 길이, 날짜·트랙 분포, 정확 중복과 근접 중복이다. D001과 D007은 근접 중복 사례이며, 무조건 삭제하지 않고 출처와 분석 목적에 따라 처리한다.

### 3.2 문장: `sentences`

각 문장은 원문 안의 위치를 함께 가진다.

```text
doc_id + sentence_id + start_char + end_char + sentence_text
```

`text[start_char:end_char] == sentence_text`를 검사하므로, 나중에 추출된 관계가 실제 원문의 어느 부분에서 나온 것인지 복원할 수 있다.

### 3.3 개체 언급: `mentions`

개체명 사전과 `EntityRuler`를 이용해 문장 안의 언급을 찾는다.

```text
mention_text + entity_type + start_char + end_char + sentence_id + doc_id
```

첫 실행에서는 `Vertex V9` 패턴을 일부러 빼 두었다. 체크포인트에서 누락을 확인한 뒤 패턴을 추가하고 `mentions`를 다시 계산한다. 이는 **오류 발견 → 제한된 수정 → 재실행**의 예다.

### 3.4 표준 개체: `entities`, `linked_mentions`

문자열 언급과 실제 개체를 구분한다.

- `Orion Labs`, `Orion` 같은 표기를 정규화해 후보를 찾는다.
- 타입과 문맥으로 하나의 표준 `entity_id`를 선택한다.
- 후보가 여러 개면 `AMBIGUOUS`, 카탈로그에 없으면 `NIL`로 남긴다.
- 억지로 기존 개체에 연결하지 않는다.

예를 들어 `Lumen Institute`는 조직 언급이지만 카탈로그에 없으므로 NIL이다. 반면 D008의 `Orion`은 개체 타입을 이용해 에이전트로 연결한다.

### 3.5 관계와 이벤트: `claims`, `events`

동일 문장에 두 개체가 등장했다는 사실만으로 관계를 만들지 않는다. 관계 트리거, 방향, 허용 타입, 부정·가정·비교 표현을 확인한 뒤 근거 문장과 함께 저장한다.

```text
claim_id
+ subject_id + predicate + object_id
+ source_doc_id + sentence_id
+ evidence_text + evidence_start + evidence_end
+ confidence + extraction metadata
```

이벤트에는 발행일과 별도로 실제 사건 시간과 상태를 둔다. `published_at`은 기사가 게시된 시점이고, `event_time`은 기사 안에서 설명한 사건의 시점이다.

## 4. 가장 중요한 개념 구분

### 언급과 개체

- **언급(mention)**: 한 문서에 실제로 등장한 문자열 범위
- **개체(entity)**: 여러 언급이 가리킬 수 있는 표준화된 대상

### 동시출현과 지식 관계

- **동시출현 그래프**: 같은 문장에 어떤 개체들이 같이 등장했는가?
- **지식 그래프**: 어떤 방향성 있는 관계가 원문 근거로 뒷받침되는가?

예를 들어 D005에서 `Atlas X`와 `Vertex V9`는 같이 등장하지만 비교 대상일 뿐이다. 따라서 동시출현 간선은 생겨도 제품 사용 관계를 나타내는 지식 간선은 만들지 않는다.

### 형식 검증과 사실성

검증은 다음 층으로 나뉜다.

1. 파싱 가능 여부
2. 필수 필드와 허용 라벨 여부
3. 관계에 맞는 주어·목적어 타입 여부
4. 저장한 위치에서 원문 근거가 정확히 복원되는지 여부
5. 그 근거가 실제로 주장을 의미하는지 여부

1~4가 통과해도 주장이 현실에서 참이라는 뜻은 아니다. 출처 자체가 틀리거나 오래됐거나 다른 출처와 충돌할 수 있으므로 출처·시간·근거를 계속 보존한다.

## 5. 그래프 생성

### 5.1 두 그래프에 공통으로 들어가는 것

두 그래프 모두 `entity_catalogue`의 모든 표준 개체를 노드로 추가한다. 각 노드에는 다음 속성이 들어간다.

```text
node ID     = entity_id
label       = 사람이 읽는 표준 이름
entity_type = ORGANIZATION, FOUNDATION_MODEL, ACCELERATOR 등
```

그래프마다 노드 집합을 다르게 만들면 간선 의미가 아니라 입력 차이 때문에 결과가 달라질 수 있다. 이 노트북은 같은 노드를 사용하고 **간선을 만드는 조건만 다르게** 해 공정하게 비교한다.

### 5.2 동시출현 그래프 `co_graph`

```python
co_graph = nx.Graph()
```

`Graph`는 무방향 단순 그래프다. 문장별로 `linked_mentions`를 묶고, `link_status == "LINKED"`인 개체 ID만 가져온다. 한 문장에 연결된 개체가 여러 개면 가능한 모든 두 개체 조합을 만든다.

예를 들어 한 문장에 `Orion Labs`, `Helios-3`, `Atlas X`가 있다면 다음 세 간선이 생긴다.

```text
Orion Labs — Helios-3
Orion Labs — Atlas X
Helios-3   — Atlas X
```

여기에는 주어·목적어 방향이나 관계 타입이 없다. 같은 쌍이 여러 문장에서 함께 등장하면 새 간선을 만들지 않고 다음 정보를 누적한다.

- `weight`: 함께 등장한 횟수
- `sentence_ids`: 함께 등장한 문장 ID 목록

따라서 이 그래프가 말할 수 있는 것은 “두 개체가 같은 문장에 있었다”뿐이다.

### 5.3 지식 그래프 `kg`

```python
kg = nx.MultiDiGraph()
```

`MultiDiGraph`의 선택에는 두 가지 이유가 있다.

- `DiGraph`: `subject → object`의 관계 방향을 보존한다.
- `Multi`: 같은 노드 쌍 사이에 여러 간선을 따로 저장한다.

`claims` 중 `validation_status == "PASS"`인 행만 간선으로 추가한다. 간선 키는 `claim_id`이므로 D001과 D007이 같은 관계를 보도해도 하나로 합쳐지지 않는다.

각 간선에는 다음 정보가 붙는다.

| 속성 | 의미 |
|---|---|
| `predicate` | `TRAINS_ON`, `SUPPLIED_BY` 같은 관계 타입 |
| `claim_id` | 해당 주장의 고유 ID |
| `source_doc_id` | 관계가 나온 문서 |
| `sentence_id` | 근거 문장 |
| `evidence_text` | 실제 근거 텍스트 |
| `published_at` | 기사 발행일 |
| `event_time` | 기사에서 설명한 사건 시점 |
| `assertion_status` | 확정, 예정, 부정, 불확실 등의 상태 |
| `confidence` | 추출 시스템의 신뢰도 |

예를 들어 다음은 단순 연결이 아니라 방향과 의미가 있는 주장이다.

```text
Helios-3 ──TRAINS_ON──▶ Atlas X
Atlas X  ──SUPPLIED_BY▶ Northstar Systems
```

### 5.4 실제 생성 결과

| 그래프 | 방향성 | 노드 수 | 간선 수 | 간선의 의미 |
|---|---:|---:|---:|---|
| 동시출현 그래프 | 없음 | 16 | 26 | 같은 문장에 등장 |
| 지식 그래프 | 있음 | 16 | 14 | 근거가 있는 타입화된 주장 |

동시출현 그래프의 간선이 더 많은 이유는 자연스럽다. 함께 언급되는 조건이 실제 관계를 주장하는 조건보다 훨씬 약하기 때문이다.

## 6. 두 그래프 비교

### 6.1 시각화 조건을 맞추는 이유

고립 노드는 그림의 가독성을 위해 숨기지만 원본 그래프에서는 삭제하지 않는다. 두 그림은 같은 `spring_layout` 좌표를 공유한다. 따라서 같은 개체가 왼쪽과 오른쪽에서 가능한 한 같은 위치에 나타나며, 간선 의미의 차이를 직접 비교할 수 있다.

노드 색은 개체 타입을 나타낸다.

- 조직: 빨간 계열
- 기반 모델: 청록 계열
- 가속기: 황금 계열
- 에이전트: 보라 계열
- 프로토콜: 녹색 계열
- 클라우드 서비스: 푸른 회색 계열
- 위치: 회색 계열

왼쪽 동시출현 그래프에는 방향과 간선 라벨이 없다. 오른쪽 지식 그래프에는 화살표와 `predicate` 라벨이 있다. 시각화할 때만 평행 간선을 하나로 접어 라벨을 합치며, 실제 `kg` 객체에는 모든 근거 간선이 그대로 남는다.

### 6.2 반례: Atlas X와 Vertex V9

D005-S01에서 두 제품은 비교 대상으로 같은 문장에 등장한다.

```text
Analysts compared Atlas X with Vertex V9.
```

실제 결과는 다음과 같다.

| 확인 항목 | 결과 |
|---|---|
| 동시출현 간선 | 있음 |
| 근거 문장 | `D005-S01` |
| 지식 그래프 간선 | 0개 |

즉, `Atlas X — Vertex V9`라는 동시출현은 관찰할 수 있지만, 한 제품이 다른 제품을 사용하거나 공급한다는 관계는 말할 수 없다. 이 예는 **가까이 등장했다는 사실과 의미 관계를 혼동하면 안 된다**는 것을 보여 준다.

## 7. 그래프 질의

### 7.1 한 개체의 근거 포함 이웃 조회

`evidence_neighbourhood(kg, entity_id)`는 해당 개체의 나가는 간선과 들어오는 간선을 따로 수집한다.

- `outgoing`: 해당 개체가 주어인 관계
- `incoming`: 해당 개체가 목적어인 관계

Helios-3 조회 결과는 다음처럼 해석한다.

| 방향 | 관계 | 이웃 | 근거 문서 |
|---|---|---|---|
| outgoing | `TRAINS_ON` | Atlas X | D001, D007 |
| incoming | `ANNOUNCED_PREVIEW` | Orion Labs | D001, D007 |
| incoming | `CONNECTS_TO` | Kestrel Agent | D003 |

D001과 D007이 같은 관계를 뒷받침하지만 각기 별도의 `claim_id`로 남아 있다. 따라서 “관계가 있다”뿐 아니라 “어떤 문서들이 그 관계를 뒷받침하는가”도 답할 수 있다.

### 7.2 다중 홉 경로 조회

질문은 “Orion Labs가 Northstar Systems와 어떻게 연결되는가?”이다. 최단 경로 탐색에서는 우선 방향을 제거한 보조 그래프 `undirected_kg`를 만든다. 이는 연결 후보를 찾기 위한 편의일 뿐, 원래 방향을 버리고 해석한다는 뜻은 아니다.

찾은 경로는 다음과 같다.

```text
Orion Labs → Helios-3 → Atlas X → Northstar Systems
```

그다음 원본 `kg`로 돌아가 경로의 각 구간을 실제 관계와 근거로 복원한다.

```text
Orion Labs ──ANNOUNCED_PREVIEW──▶ Helios-3
Helios-3   ──TRAINS_ON──────────▶ Atlas X
Atlas X    ──SUPPLIED_BY────────▶ Northstar Systems
```

각 구간에는 D001과 D007의 평행 근거가 있어 표에는 총 6개 claim이 나온다. 중요한 점은 최단 경로 자체가 설명이 아니라는 것이다. 답변으로 사용하려면 다음을 모두 점검해야 한다.

1. 원래 간선 방향이 질문의 논리와 맞는가?
2. `predicate`가 실제로 필요한 의미인가?
3. 근거 문장이 관계를 명시적으로 뒷받침하는가?
4. 여러 근거가 독립 출처인가, 근접 중복 기사인가?
5. 발행일과 사건 시점이 질문의 시간 범위와 맞는가?

## 8. 관계 추출 평가

### 8.1 그래프가 아니라 추출 결과를 평가하는 이유

그래프 그림이 자연스러워 보여도 간선이 틀릴 수 있다. 따라서 먼저 그래프의 입력인 `claims`를 평가한다. 평가 단위는 다음 네 항목의 엄격한 튜플이다.

```text
(source_doc_id, subject_id, predicate, object_id)
```

`source_doc_id`를 포함했기 때문에 D001과 D007의 같은 관계를 서로 다른 근거로 계산한다. 반대로 출처를 제외하면 동일 트리플을 하나로 합치는 별도의 평가가 된다. 어떤 방식을 택하든 평가 단위를 명시해야 한다.

### 8.2 TP, FP, FN 계산

```text
TP = predicted_claims ∩ gold_claims
FP = predicted_claims - gold_claims
FN = gold_claims - predicted_claims
```

- **TP(True Positive)**: 정답에도 있고 시스템도 추출한 관계
- **FP(False Positive)**: 시스템은 추출했지만 정답에는 없는 관계
- **FN(False Negative)**: 정답에는 있지만 시스템이 놓친 관계

이 노트북의 기본 lexical baseline 결과는 다음과 같다.

| TP | FP | FN | Precision | Recall | F1 |
|---:|---:|---:|---:|---:|---:|
| 14 | 0 | 1 | 1.000 | 0.933 | 0.966 |

계산식은 다음과 같다.

```text
Precision = TP / (TP + FP) = 14 / 14 = 1.000
Recall    = TP / (TP + FN) = 14 / 15 = 0.933
F1        = 2 × Precision × Recall / (Precision + Recall) = 0.966
```

해석하면, 추출한 14개는 모두 맞았지만 정답 15개 중 하나를 놓쳤다. 즉 이 시스템은 보수적이며 정밀도는 높지만 재현율에 작은 누락이 있다.

### 8.3 오류 분석

유일한 오류는 다음 FN이다.

```text
D009: Kestrel Agent ──SUPPORTS_PROTOCOL──▶ AgentMesh
```

D009의 두 번째 문장은 `AgentMesh`를 다시 직접 쓰지 않고 `the protocol`이라고 지칭한다. 기존 관계 추출기는 같은 문장 안에서 명시적으로 연결된 개체를 중심으로 동작하므로 이 대상을 찾지 못한다.

이것은 관계 라벨 분류 실패라기보다 **문장 간 지시 표현 해결 실패**다. 이렇게 오류 원인을 특정해야 적절한 개선 방법을 고를 수 있다.

## 9. 오류 기반 확장 A: 제한적 상호참조 해결

개선 가설은 다음과 같다.

> D009에서 `the protocol`을 직전 문장의 가장 최근 PROTOCOL 개체에 연결하면 FP를 늘리지 않고 FN 하나를 복구할 수 있다.

수정 범위는 의도적으로 좁다.

```text
문서: D009
표현: "the protocol"
후보: 직전 문장에서 LINKED된 가장 최근 PROTOCOL
복구 관계: Kestrel Agent ──SUPPORTS_PROTOCOL──▶ AgentMesh
```

수정 전후 결과는 다음과 같다.

| 시스템 | Precision | Recall | F1 |
|---|---:|---:|---:|
| lexical baseline | 1.000 | 0.933 | 0.966 |
| + narrow protocol coreference | 1.000 | 1.000 | 1.000 |

이 예제에서 점수가 완벽해졌다고 해서 일반 상호참조 문제가 해결된 것은 아니다. 새 규칙은 D009에 맞춘 제한적 수정이며, 더 큰 데이터에서는 다음을 별도로 확인해야 한다.

- 멀리 떨어진 선행사를 잘못 고르지 않는가?
- 한 문서에 프로토콜이 여러 개일 때 모호성을 처리하는가?
- `this protocol`, `it`, `the standard` 같은 다른 표현에도 적용할 것인가?
- 관계 타입별·주제별·시기별·출처별로 성능이 유지되는가?
- NIL과 AMBIGUOUS 링크 비율이 변하지 않는가?

핵심 개선 순서는 다음과 같다.

```text
오류 목록 확인
  → 실패 단계 진단
  → 하나의 검증 가능한 가설 설정
  → 범위가 작은 규칙 추가
  → 같은 gold set으로 재평가
  → 새 FP와 다른 하위 집단 성능 점검
```

## 10. 확장 B: 구조화된 LLM 관계 추출

### 10.1 LLM이 맡는 역할

기존 lexical rule 대신 LLM이 다양한 표현에서 **관계 후보를 제안**할 수 있다. 하지만 LLM의 출력이 바로 지식 그래프 간선이 되는 것은 아니다.

```text
스키마 + 원문
  → LLM 후보 JSON
  → Pydantic 형식 검증
  → 언급을 표준 개체 ID에 연결
  → 관계 타입 조합 검증
  → 인용문과 원문 대조
  → 의미 검토
  → 채택 또는 거절
```

### 10.2 Pydantic이 검사하는 것

`ClaimCandidate`는 각 후보가 다음 필드를 갖도록 강제한다.

```text
subject_mention
predicate
object_mention
evidence_quote
assertion_status
confidence
```

- `predicate`는 미리 허용한 11개 관계 중 하나여야 한다.
- `assertion_status`는 `ASSERTED`, `PLANNED`, `NEGATED`, `UNCERTAIN` 중 하나여야 한다.
- `confidence`는 0.0~1.0 범위여야 한다.
- `ExtractionBatch`는 문서 ID와 후보 목록을 묶는다.

따라서 잘못된 라벨이나 범위를 벗어난 신뢰도 같은 **형식 오류**는 잡을 수 있다. 그러나 주어와 목적어를 뒤집었거나 원문 의미를 과장한 경우까지 자동으로 참이라고 보증하지는 않는다.

### 10.3 근거 인용 검사

모의 D003 응답에는 다음 두 후보가 있다.

```text
Nebula ──INTRODUCED──▶ AgentMesh
Kestrel Agent ──CONNECTS_TO──▶ Helios-3
```

`validate_evidence_quotes`는 각 `evidence_quote`가 D003 원문에 정확히 포함되는지 확인한다. 두 후보 모두 `quote_found_verbatim == True`이므로 다음 단계인 개체 연결과 타입 검증으로 보낼 수 있다.

이 검사가 실패하면 후보를 즉시 채택하지 않고 다음 중 하나를 수행해야 한다.

- 근거 없는 후보로 거절
- 위치·공백·정규화 문제인지 제한적으로 복구
- 사람이 원문을 검토

### 10.4 프롬프트가 보수적으로 설계된 이유

프롬프트에는 허용 관계 목록과 다음 규칙이 들어간다.

1. 원문이 명시적으로 뒷받침하는 관계만 반환한다.
2. 후보마다 최소한의 원문 인용을 복사한다.
3. 부정·불확실·예정 상태를 보존한다.
4. 모호한 언급은 추측해 연결하지 않는다.
5. 관계가 없으면 빈 목록을 반환해도 된다.

D005는 좋은 시험 문서다. `Atlas X`와 `Vertex V9`가 비교되며, 다음 문장은 Orion Labs가 Vertex V9을 사용했다는 사실을 **말하지 않았다고 명시**한다. 올바른 출력은 사용 관계를 만들어 내는 것이 아니라 빈 후보 목록이거나 명시적인 거절이다.

### 10.5 구조화 출력이 보장하지 않는 것

구조화 출력은 JSON 문법과 필드 타입을 안정시킬 수 있지만 다음은 별도 검증 대상이다.

- 인용문이 실제로 존재하는가?
- 인용문이 해당 관계를 의미하는가?
- 부정이나 불확실성을 놓치지 않았는가?
- 표면 문자열이 올바른 표준 개체에 연결됐는가?
- 관계의 주어·목적어 타입과 방향이 맞는가?
- 출처가 신뢰할 만하고 최신인가?

실제 API를 연결한다면 제공자, 모델 ID, 프롬프트 버전, 디코딩 설정, 실행 시각을 함께 저장해야 결과를 재현하고 모델 변경 전후를 비교할 수 있다.
